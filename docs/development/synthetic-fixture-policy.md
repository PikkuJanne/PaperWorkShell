# Synthetic document fixture and restricted-sample policy

- Status: Binding foundation policy
- Task: PWS-0009
- Decision: PWS-D035
- Last reviewed: 2026-08-01

PaperWorkShell treats every document and image as hostile and potentially sensitive. The routine
repository and CI corpus is therefore **public synthetic-only**: it is built from fixed algorithms
and reviewed literals, never from a person, applicant, customer, bug report, or downloaded file.
Removing a name or metadata from a real document does not make that document eligible for this
corpus.

## Public corpus contract

The version-1 corpus is indexed by
[`tests/fixtures/synthetic/v1/index.json`](../../tests/fixtures/synthetic/v1/index.json). Its closed metadata contract is
[`synthetic-fixture-index-v1.schema.json`](../../schemas/synthetic-fixture-index-v1.schema.json).
Every committed PDF and PNG:

- is generated without document input, network access, subprocesses, randomness, clock values,
  locale values, usernames, or host paths;
- contains the uncompressed `PWS-SYNTHETIC-FIXTURE` marker;
- has an exact path, byte count, SHA-256 digest, recipe, construction assertions, categories, and
  generated provenance in the index;
- is smaller than the committed-fixture limit and is regenerated byte-for-byte during validation;
- contains no real identity, address, financial, medical, employment, handwriting, signature, or
  applicant material.

The marker is a useful signal, not proof of safety. The primary assurance is closed no-input
generation plus exact inventory and byte comparison. Index properties are construction assertions;
they do not claim that a future PDF/image engine has parsed, rendered, decrypted, extracted, or
visually verified the artifact.

The index covers each roadmap corpus class as `committed`, `on-demand`, or `scheduled`. A
`scheduled` entry names the task that can honestly construct and verify the class:

- protected/encrypted PDF behavior: PWS-0105;
- CMYK image behavior: PWS-0201;
- rendered multilingual and complex-script text: PWS-0303;
- right-to-left layout behavior: PWS-0704.

The Unicode category is committed as an NFC Unicode-named PDF path, which needs no font or feature
engine. It does not claim rendered Unicode page content; that distinct behavior remains with the
font strategy task.

The signed-marker fixture contains an unsigned PDF signature field only. It is not a digital
signature, does not contain a signature image, and carries no validity claim. The script-marker
fixture contains an orphaned structural token that is unreachable from the document catalog. The
handwriting demonstration is an algorithmic abstract stroke pattern explicitly marked as not a
signature.

## Regeneration and validation

Use the registered commands:

```powershell
py -3.14 tools/dev.py generate-fixtures
py -3.14 tools/dev.py validate-fixtures
```

`generate-fixtures` is intentionally mutating and is not part of `check`. It writes only the
reviewed committed artifacts and canonical index and refuses an unexpected output inventory.
Review every generator or byte change; do not refresh fixtures merely to make a test pass.

`validate-fixtures` is non-mutating. It authenticates the schema, validates current and rejected
index examples, reconstructs the expected bytes in memory, compares the exact corpus, and applies
the repository document-data policy to the hardened Git/index/working-tree snapshot shared with
the secret-scanning boundary. Reachable historical, root/pseudo-ref, direct blob/tree, exact index,
tracked, and nonignored untracked document/image bytes must either match an approved generated
fixture digest or validation fails. High-confidence structured-data patterns are also rejected
without echoing the matched path or value. Git author, committer, tagger, and folded-mergetag
identity records are provenance rather than fixture content; Gitleaks still scans their raw bytes
in the separate `scan-secrets` lane.

IBAN detection uses the fixed country lengths in the
[SWIFT IBAN Registry Release 102](https://www.swift.com/swift_resource/9606) (June 2026) and
performs one checksum validation per recognized candidate. Payment-card detection is deliberately
limited to reviewed, high-confidence issuer and length ranges, with mixed visual separators parsed
as bounded group candidates. Non-issuer numeric streams trigger no checksum work, and pathological
issuer-shaped streams fail closed at a fixed candidate budget. Those ranges are privacy guardrails,
not an exhaustive card-brand classifier.

These pattern checks are guardrails, not anonymization or a proof that arbitrary prose, compressed
streams, encrypted content, or raster pixels contain no personal information. No external document
is made acceptable by passing a scan. Exact closed generation is the admission rule.

## On-demand hostile recipes

Very-large and long-path inputs are generated only by an explicit `on-demand` recipe into a
caller-owned directory outside the repository. The generator refuses repository-local output,
unsafe sizes, and overwrite. The caller must use a temporary or access-controlled local directory,
run only the smallest profile needed, and remove the output when the test finishes. These files are
never attached to routine CI, GitHub issues, pull requests, caches, or artifacts.

Example:

```powershell
py -3.14 -m tools.generate_synthetic_fixtures on-demand oversized-pdf --output-directory C:\pws-fixture-temp
```

The default oversized recipe is intentionally above the ordinary scanner limit. Routine tests use
small bounded profiles and do not create the default large file.

## Restricted bug samples outside the repository

When a bug is reported against a real document:

1. Record only an internal incident/reference ID and generic technical properties in routine
   issues or logs. Do not record the original filename, full path, extracted text, metadata,
   thumbnail, form value, handwriting, or person details.
2. Reproduce the behavior from scratch with the smallest synthetic document possible. Admit only
   that new closed recipe and its reviewed generated bytes.
3. If the original is still essential, obtain explicit maintainer authorization and place it in
   maintainer-controlled restricted storage outside the repository, its parent directories,
   synchronized folders, ordinary diagnostic exports, and CI workspaces. Grant minimum access and
   define a retention/deletion date.
4. Never commit, stage, paste, screenshot, encode, attach, or publish the sample or a content hash in
   Git, GitHub, a routine task, a pull request, CI, chat, email, or an ordinary bug tracker.
5. Treat metadata removal, page cropping, black boxes, OCR deletion, and filename changes as
   insufficient anonymization. PDFs may retain incremental revisions, attachments, forms,
   thumbnails, signatures, metadata, and recoverable content.
6. Delete the restricted copy at the approved retention point and record only the generic incident
   outcome. Do not make deletion claims for storage outside maintainer control.

An accidental stage, commit, upload, or paste is a security/privacy incident. Stop distribution and
follow the maintainer incident process; deleting the current file is insufficient because Git
history, clones, caches, and remote retention may persist.

## Adding or changing a fixture

An addition requires a named recipe, closed provenance, reciprocal category coverage, success and
failure tests, exact regeneration, privacy scanning, and an explanation of why an existing fixture
is insufficient. Corpus versions are immutable once consumed by released migrations or golden
evidence; later incompatible changes use a new version rather than silently changing version-1
meaning.
