# Synthetic document fixture and restricted-sample policy

- Status: Binding foundation policy
- Task: PWS-0009
- Decision: PWS-D035
- Last reviewed: 2026-08-22

PaperWorkShell treats every document and image as hostile and potentially sensitive. The routine
repository and CI corpus is therefore **public synthetic-only**: it is built from fixed algorithms
and reviewed literals, never from a person, applicant, customer, bug report, or downloaded file.
Removing a name or metadata from a real document does not make that document eligible for this
corpus.

## Public corpus contract

The version-1 corpus is indexed by
[`tests/fixtures/synthetic/v1/index.json`](../../tests/fixtures/synthetic/v1/index.json). Its closed metadata contract is
[`synthetic-fixture-index-v1.schema.json`](../../schemas/synthetic-fixture-index-v1.schema.json).
Every committed PDF and PNG:

- is generated without document input, network access, subprocesses, randomness, clock values,
  locale values, usernames, or host paths;
- contains the uncompressed `PWS-SYNTHETIC-FIXTURE` marker;
- has an exact path, byte count, SHA-256 digest, recipe, construction assertions, categories, and
  generated provenance in the index;
- is smaller than the committed-fixture limit and is regenerated byte-for-byte during validation;
- contains no real identity, address, financial, medical, employment, handwriting, signature, or
  applicant material.

The marker is a useful signal, not proof of safety. The primary assurance is closed no-input
generation plus exact inventory and byte comparison. Index properties are construction assertions;
they do not claim that a future PDF/image engine has parsed, rendered, decrypted, extracted, or
visually verified the artifact.

The index covers each roadmap corpus class as `committed`, `on-demand`, or `scheduled`. PWS-0105
adds a deterministic password-required PDF and a separate catalog-reachable action-only PDF.
PWS-0106 adds font-free PDF renderer calibration, inherited and direct page boxes, all four
quarter-turn rotations, non-default `UserUnit` observation, ordinary alpha, a soft mask and
multiply blend mode,
PDF DeviceCMYK and ICCBased structures, a stored annotation appearance, a synthetic embedded Type3
font, an unembedded synthetic Type1 missing-font fallback case, high page dimensions, complete
framing with a broken page tree, and analytical RGB reference images. These are construction
assertions and independent analytical oracles, not evidence that a selected renderer has executed
them. PWS-0303 adds a separate standard-library Type3 carrier whose explicit `ToUnicode` CMap
extracts the fixed synthetic sample `PWS café ΩΔ ЖЯ`. Its four generated geometric CharProcs and
Latin, Greek, and Cyrillic mappings use no product font, system font, downloaded asset, or external
source material. A `scheduled` entry names a later task that can honestly construct and verify the
remaining class:

- right-to-left layout behavior: PWS-0704.

The committed `cmyk` category is deliberately limited to PDF rendering: it contains DeviceCMYK
vector swatches, a tiny algorithmic DeviceCMYK image XObject, and a separate ICCBased image with a
deterministic standards-valid ICC v2.1 linear-RGB monitor profile plus an explicit DeviceRGB
alternate. The profile has `desc`, `cprt`, `wtpt`, three colorant, and three shared-curve TRC tag
records and is capability-checked through the installed Pillow/lcms boundary. CMYK-to-RGB values
depend on the selected color-management implementation, so the corpus records the structures and
swatch relationships without inventing an exact RGB golden. Predictable CMYK behavior for
standalone JPEG/PNG intake is proved separately by PWS-0201's algorithmic in-memory image corpus;
it is not claimed by these PDF renderer fixtures.

The Unicode category remains an NFC Unicode-named PDF path, which needs no font or feature engine.
The separate multilingual category is an extraction and font-resource construction oracle. Its
abstract glyph programs deliberately do not claim product-font appearance, complex shaping, or
right-to-left layout behavior; those properties require the renderer and font-strategy evidence
owned by their implementation tasks.

The password-required fixture uses a deterministic, test-only weak Standard Security Handler R2
construction and a public synthetic password token recorded in the index. It exists only to prove
the closed `encrypted` inspection state; it is not an approved encryption profile or sensitive
credential. The action-only fixture contains one catalog action and no JavaScript marker, while the
script-marker fixture contains an orphaned structural token unreachable from the document catalog.
Their shared index category preserves the released schema vocabulary; adapter tests distinguish the
two construction assertions.

The embedded-font renderer case uses a PDF Type3 font whose one geometric glyph procedure is
generated from fixed operators. The multilingual carrier uses four similarly generated procedures
plus an explicit twelve-entry `ToUnicode` mapping. Neither contains a copied font program, system
font, third-party font asset, or external text sample. They prove only their indexed resource,
mapping, extraction, and bounded-rendering properties; product Unicode font selection and shaping
remain separately gated.

The missing-font case names a repository-owned synthetic BaseFont but deliberately embeds no font
program. Its selected-renderer oracle is semantic rather than a captured bitmap: rendering must
produce a bounded, non-empty, opaque fallback glyph region inside the declared page. Exact pixels
or a warm-process digest are not stable evidence because fallback-font selection and renderer font
caches may vary across otherwise supported Windows environments. The case therefore documents
fallback behavior without adding or claiming a product font strategy before PWS-0303.

The renderer references indexed by
[`tests/golden/renderer-v1/index.json`](../../tests/golden/renderer-v1/index.json) are not
captured renderer output. They are independently calculated, font-free RGB8 top-down oracles at one
pixel per PDF user unit. Each PNG is byte-identical to an indexed public synthetic image, so the
repository privacy scanner authorizes it by the same reviewed digest. The golden index binds the
PDF fixture digest, an explicit page-box/additional-rotation/fit-bounds request, intrinsic and
combined rotations, user-unit render scale, dimensions, pixel layout, comparison mode, and
reference digest.
Geometry, stored-appearance, and synthetic Type3 references compare exactly. The ordinary
half-alpha reference and the soft-mask/blend reference permit only a one-channel-value rounding
difference. The PDF 1.6 geometry matrix separately binds inherited boxes at intrinsic 0, 90, 180,
and 270 degrees; page-zero requests with additional 90, 180, and 270 degree turns; four distinct
opposing crop-to-media insets; a page with direct boxes; and a `UserUnit` page rendered at one pixel
per user unit. CMYK and ICCBased cases are intentionally checked by documented structures and
swatch relationships rather than an invented device-independent RGB value.

PWS-0202 uses a separate `image-transforms-v1` golden family because fine deskew, resampling, and
tonal cleanup are pinned production-profile behavior rather than independent PDF analytical
oracles. Its six sources are still closed, no-input, standard-library-generated public rasters:
asymmetric corners, a crop grid, a deskew line grid, a grayscale ramp, a synthetic paper/stroke
field, and an alpha canary. No source image is copied from a user or downloaded file. The committed
set contains only approved deterministic RGBA8 PNG outputs plus a canonical index; sources are
reconstructed from their bound recipes.

[`tools/image_transform_goldens.py`](../../tools/image_transform_goldens.py) cannot execute or
import the production transform. It accepts already-produced bounded RGBA8 results and first stages
a candidate outside the repository with exact source/operation/output digests and a labeled
before/after HTML review sheet. Candidate status is explicitly unapproved. After all six pairs are
inspected at native and enlarged nearest-neighbour scale, a separate explicit recorded visual approval
step creates a closed promotion inventory outside the repository. Only that index and those six
PNGs may be copied into `tests/golden/image-transforms-v1`; the review sheet, temporary sources, and
candidate directory never enter Git.

The image-transform validator rejects a missing or extra entry, link/reparse point, hard link,
noncanonical JSON or PNG, wrong source recipe, stage reordering, operation or pixel digest change,
nonopaque result, dimension change, duplicate key, or absent approval. A production profile or
expected-pixel change requires a reviewed version-2 set and rationale; no command automatically
refreshes the approved version-1 files. The exact transform order, case matrix, and review checklist
are defined in the
[image-transform pipeline contract](../architecture/image-transform-pipeline.md).

The signed-marker fixture contains an unsigned PDF signature field only. It is not a digital
signature, does not contain a signature image, and carries no validity claim. The handwriting
demonstration is an algorithmic abstract stroke pattern explicitly marked as not a signature.

## Regeneration and validation

Use the registered commands:

```powershell
py -3.14 tools/dev.py generate-fixtures
py -3.14 tools/dev.py validate-fixtures
```

`generate-fixtures` is intentionally mutating and is not part of `check`. It writes only the
reviewed committed corpus, canonical corpus index, and analytical renderer references, and refuses
an unexpected output inventory. Review every generator or byte change; do not refresh fixtures or
goldens merely to make a test pass. It does not capture or approve PWS-0202 transform output; that
family uses the separate review workflow above.

`validate-fixtures` is non-mutating. It authenticates the schema, validates current and rejected
index examples, reconstructs the expected bytes in memory, compares the exact corpus and renderer
golden inventory, and applies the repository document-data policy to the hardened
Git/index/working-tree snapshot shared with the secret-scanning boundary. Reachable historical,
root/pseudo-ref, direct blob/tree, exact index, tracked, and nonignored untracked document/image
bytes must either match an approved generated fixture digest or validation fails. High-confidence
structured-data patterns are also rejected without echoing the matched path or value. Git author,
committer, tagger, and folded-mergetag identity records are provenance rather than fixture content;
Gitleaks still scans their raw bytes in the separate `scan-secrets` lane.

IBAN detection uses the fixed country lengths in the
[SWIFT IBAN Registry Release 102](https://www.swift.com/swift_resource/9606) (June 2026) and
performs one checksum validation per recognized candidate. Payment-card detection is deliberately
limited to reviewed, high-confidence issuer and length ranges, with mixed visual separators parsed
as bounded group candidates. Non-issuer numeric streams trigger no checksum work, and pathological
issuer-shaped streams fail closed at a fixed candidate budget. Canonical UUID tokens are excluded
before financial candidates are evaluated. Those ranges are privacy guardrails, not an exhaustive
card-brand classifier.

These pattern checks are guardrails, not anonymization or a proof that arbitrary prose, compressed
streams, encrypted content, or raster pixels contain no personal information. No external document
is made acceptable by passing a scan. Exact closed generation is the admission rule.

## On-demand hostile recipes

Very-large and long-path inputs are generated only by an explicit `on-demand` recipe into a
caller-owned directory outside the repository. The generator refuses repository-local output,
unsafe sizes, and overwrite. The caller must use a temporary or access-controlled local directory,
run only the smallest profile needed, and remove the output when the test finishes. These files are
never attached to routine CI, GitHub issues, pull requests, caches, or artifacts.

Example:

```powershell
py -3.14 -m tools.generate_synthetic_fixtures on-demand oversized-pdf --output-directory C:\pws-fixture-temp
```

The default oversized recipe is intentionally above the ordinary scanner limit. Routine tests use
small bounded profiles and do not create the default large file.

## Restricted bug samples outside the repository

When a bug is reported against a real document:

1. Record only an internal incident/reference ID and generic technical properties in routine
   issues or logs. Do not record the original filename, full path, extracted text, metadata,
   thumbnail, form value, handwriting, or person details.
2. Reproduce the behavior from scratch with the smallest synthetic document possible. Admit only
   that new closed recipe and its reviewed generated bytes.
3. If the original is still essential, obtain explicit maintainer authorization and place it in
   maintainer-controlled restricted storage outside the repository, its parent directories,
   synchronized folders, ordinary diagnostic exports, and CI workspaces. Grant minimum access and
   define a retention/deletion date.
4. Never commit, stage, paste, screenshot, encode, attach, or publish the sample or a content hash in
   Git, GitHub, a routine task, a pull request, CI, chat, email, or an ordinary bug tracker.
5. Treat metadata removal, page cropping, black boxes, OCR deletion, and filename changes as
   insufficient anonymization. PDFs may retain incremental revisions, attachments, forms,
   thumbnails, signatures, metadata, and recoverable content.
6. Delete the restricted copy at the approved retention point and record only the generic incident
   outcome. Do not make deletion claims for storage outside maintainer control.

An accidental stage, commit, upload, or paste is a security/privacy incident. Stop distribution and
follow the maintainer incident process; deleting the current file is insufficient because Git
history, clones, caches, and remote retention may persist.

## Adding or changing a fixture

An addition requires a named recipe, closed provenance, reciprocal category coverage, success and
failure tests, exact regeneration, privacy scanning, and an explanation of why an existing fixture
is insufficient. Corpus versions are immutable once consumed by released migrations or golden
evidence; later incompatible changes use a new version rather than silently changing version-1
meaning.

For a captured transform golden, “closed recipe” also includes the exact immutable source recipe,
canonical operation bytes, intent/cache/artifact versions, transform and strict-normalization
profile digests, pinned pixel-affecting dependency versions, output layout and dimensions, output
digest, and recorded human approval. Merely recapturing a current production result is not an
acceptable update procedure.
