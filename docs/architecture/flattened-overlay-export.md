# Verified flattened visual-overlay export

- Status: Binding implementation contract
- Task: PWS-0307
- Decisions: PWS-D018, PWS-D020, PWS-D029, PWS-D037
- Base contract: [Deterministic verified PDF export](pdf-export.md)
- Rendering contract: [Deterministic overlay rendering](overlay-rendering.md)

## Scope and limited claims

PWS-0307 adds `pdf.export.flattened` version 1 without changing `pdf.export` version 1. The new
path exports the current manifest page sequence, active crop, accumulated quarter-turn rotation,
and visible overlay stack into a new unencrypted PDF. Text, dates, initials, checks, crosses,
simple visual shapes, and placed signature images become ordinary page content. Imported originals
and existing external destinations are never modified or replaced.

The transient flattened-export report wraps the unchanged structural export report and adds only
four closed facts: visible overlays were flattened; the reopened structure retained each exact
planned Form placement and every page rendered; the approved embedded-font strategy was checked;
and placed signature images remained visual marks rather than digital signatures. It does not
claim PDF/UA, PDF/A, legal validity, cryptographic signing, permanent redaction, portal acceptance,
pixel-perfect rendering in every viewer, or universal compatibility.

The interaction claim is deliberately local to content generated by this feature. Page-local source
content, resources, annotation dictionaries, and stored appearance graphs are copied and bound;
catalog-dependent widget, action, named-destination, and similar behavior is not certified.
Optional-content dependencies are rejected because their visibility policy lives in the source
Catalog and cannot be preserved by the page-copy composition. PWS-0105/preflight reports source
features, and PWS-0405/PWS-0501 own the later unsupported-content policy. Flattened overlay Forms
themselves contain no annotations, widgets, actions, scripts, XFA, attachments, or appearance
dependency.

## Plan and application sequence

`required_visible_signature_assets` and `build_flattened_pdf_export_plan` reconstruct the active
page projection and overlay collection from one immutable manifest snapshot. Invisible overlays,
inactive pages, and overlays wholly outside the active crop do not enter the plan. Visible records
retain deterministic low-to-high z-order. Source order and signature-asset order are canonical
first-use order. Case, source, page, overlay, and asset UUID namespaces are pairwise disjoint.

The semantic fingerprint covers the versioned base PDF intent, active crop per output page, every
visible overlay payload and box, and exact raster metadata. Authority-only revision, CAS token, and
case identity remain outside the semantic hash but are independently checked for freshness.

Before image decode, the application builds an inert metadata-only planning projection. That
projection determines the exact sources/pages, enforces signed-source modification consent, checks
destination capacity, and establishes the numeric page total for progress. Placeholder raster
metadata is never transferred or reported. Committed placed-signature assets are then decoded one
at a time through the existing restricted image worker. The actual authenticated RGBA8 metadata
builds the executable plan, whose base/page projection must exactly equal the planning projection.

The decoded rasters remain bounded volatile values. The requested square edge and aggregate raster
allowance derive from `OverlayRenderLimits.from_resource_policy`: no single raster exceeds the
policy pixel/byte limits and all retained rasters together use at most the policy's established
one-thirty-second worker-memory allowance. Rasterization finishes before the flattened export
broker acquires the shared heavy-operation lease, avoiding nested acquisition deadlock.
Each returned raster must also fit the exact requested width and height and retain exact
`width * 4` row-stride and `stride * height` byte relationships before it can enter a plan.

## Handle-only operation

The broker creates one distinct operation ID, plan object ID, output object ID, and reduced handle
for each admitted authority. Its ordered inputs are:

1. one `OPERATION_TEMP` canonical plan section;
2. exact immutable PDF `SOURCE_READ` references in first-use order; and
3. exact operation-scoped `OPERATION_TEMP` RGBA8 sections in signature-asset order.

Each raster reference uses content kind `overlay-rgba8-v1`, exact byte count, and pixel SHA-256.
Raster handles appear only in the canonical worker plan; there is no path, filename, encoded JPEG
or PNG, or ambient asset-directory authority. The output is one fixed-capacity section and the
content-free report uses one bounded pipe. All handles and correlation UUIDs must be distinct.
The additive operation admits at most the protocol's 256 input references, including the plan,
all source PDFs, and all raster sections. The application checks that total on its metadata-only
plan before consent, capacity preflight, image decode, handle creation, or worker launch; the broker
rechecks it before binding or allocating any authority.

After start, the broker pumps validated page progress and cancellation. It terminates the complete
one-shot worker tree before revalidating retained PDF sources or reading the report/output. It then
binds operation/output IDs, semantic fingerprint, page count, unsigned-derivative state, exact
checks, byte size, and digest. Only an authenticated bounded candidate reaches destination code.

## Worker staging and resource bounds

The worker consumes the plan handle, discovers the source/raster handles, and owns each transferred
authority exactly once. PDF handles are copied and rehashed into the authenticated worker-private
operation directory before pikepdf sees them. RGBA handles are mapped read-only, authenticated in
bounded chunks, exposed as seekable renderer sources, and unmapped before operation return. The
encoded signature image is never reparsed by the flattened-export worker.

Operation limits account for plan, PDF sources, raster sections, candidate output, page count,
total raster pixels, process memory, private temporary storage, wall time, and CPU time. Overlay
limits preserve the established peak equation: ten times retained raster allowance plus six times
intermediate overlay output must fit after reserving one quarter of process memory for engines,
fonts, and other operation state. Sources and page intermediates are processed serially. There is
no unbounded cache, queue, executor, process count, or whole-document full-resolution raster set.
The bounded file-copy/hash chunk is derived independently from available worker memory rather than
from retained signature-raster bytes, so a text-only overlay plan remains operable while every I/O
chunk still fits its admitted memory budget.

Cancellation, timeout, malformed plan/reference, source or asset change, mapping failure,
disk-full, output overflow, and cleanup failure produce closed content-free errors. Partial worker
candidates remain inside the pinned private operation directory and are removed during cleanup.

## Explicit Form-XObject composition

For each output page, the adapter resolves effective MediaBox/CropBox, inherited `/Rotate`,
`/UserUnit`, and the nearest inherited `/Resources`; selects the active crop; and asks the approved
overlay renderer for one verified self-contained page. It converts that page with
`as_form_xobject(handle_transformations=False)`, imports the Form into the output document, clones
inherited resource dictionaries before mutation, and isolates source content with `q`/`Q`.

The appended invocation is exactly `q <matrix> cm /PWSOverlayN Do Q`. The recorded matrix maps the
renderer canvas back into raw source user space. Manifest crop is materialized in raw coordinates,
then accumulated rotation is materialized on the output page. `/UserUnit` remains explicit. The
adapter never calls pikepdf `add_overlay()` and does not rely on annotation, widget, AcroForm,
viewer-generated appearance, JavaScript, action, attachment, XFA, or incremental-update behavior.

Before choosing `PWSOverlayN`, the adapter performs a bounded conservative scan for existing `Do`
operands in source page content and reachable resource streams, including nested Forms and Type 3
font character procedures. Every observed name is reserved even when its current resource lookup
is unresolved. Adding the overlay resource therefore cannot activate a dormant source invocation.

Direct source page content is parsed as one concatenated sequence before composition. Graphics
state (`q`/`Q`), text objects (`BT`/`ET`), marked content (`BMC` or `BDC`/`EMC`), and compatibility
sections (`BX`/`EX`) must never underflow and must finish balanced; parser warnings or ambiguity
fail closed. Ordinary marked content remains supported, but `/OC` marked content and page-reachable
OCG, OCMD, or `/OC` dependencies fail closed because their Catalog policy is not copied. The
ordered decoded source-content streams are length-delimited and fingerprinted
before the wrapper is added. Reopen verification requires the exact wrapper streams, the same
middle-stream fingerprint, and the same balanced middle sequence, preventing saved-output changes
from leaking a crop, transform, text object, or optional-content scope into the overlay invocation.

Candidate serialization preserves copied stream representations: it neither decodes streams nor
compresses/recompresses source streams. Raw streams, filter arrays, decode parameters, and opaque
image/font encodings therefore remain stable for the bounded source-graph fingerprint; decoded
content semantics are bound separately.

Text Forms must contain the approved embedded Type0/CIDFontType2 font, `FontFile2`, `ToUnicode`, and
the renderer's supported `ActualText` path. Placed signature images use only authenticated RGBA8
pixels embedded as visual image XObjects. Their terminology and report claims explicitly state that
placing the image did not create a digital signature.

## Verification before publication

The adapter completes all of the following before a report exists:

1. strictly reopen without recovery and reject encryption, malformed structure, page-count or
   effective page-geometry mismatch;
2. require the exact per-page resource name, Form BBox, single `Do`, placement matrix, isolated
   content sequence, font/image resource counts, and prohibited-interactive-key absence throughout
   the generated overlay Form graph;
3. compare a bounded canonical fingerprint of the complete generated Form object graph with the
   pre-save fingerprint, including decoded reachable streams, so blanked or changed root and nested
   streams cannot satisfy presence verification;
4. render both the trusted overlay page and a one-page harness invoking the actual normalized,
   imported Form serially against white and verification-only black backgrounds; require identical
   independently authenticated raster results. Opaque text, marks, and vector paint whose request
   region spans at least one verification pixel must differ from at least one background. Partial-
   alpha paint gets that requirement only for a full-bbox dense rectangle fill, or for a signature
   window whose every contributing alpha sample is at least two. Other sparse partial-alpha paint
   and sparse rasters retain the exact differential proof without a false fixed-resolution
   rejection. Alpha-byte-1 paint remains effective and preserved even when 8-bit compositing rounds
   it away. Empty/no-ink text, zero-alpha vector intent, crop-hidden raster alpha, and an all-
   transparent signature remain valid no-paint placements;
5. run the fixed qpdf 12.3.2 check without a shell;
6. render every output page with the approved PDFium profile under bounded pixels/memory/time;
7. revalidate every staged source stream and remeasure the candidate; and
8. emit the report only when the final size and SHA-256 remain unchanged.

Injected missing, blanked, clipped-away, graph-changed, or grossly displaced Form placement fails
the graph, placement, full-raster equivalence, request-region, or reopen checks and deletes the
candidate. The two background probes are
streaming and serial: they retain one bounded row, use changed-pixel row prefixes for bounded region
queries, and share the operation's existing pixel, memory, output-byte, and deadline limits. The
verification-only black-underlay copy uses a separate bounded two-times output headroom inside the
existing six-output memory reserve, so insufficient reserialization headroom fails closed.
Final-page renderer success proves that retained page content
remains renderable; it is not described as a cross-viewer pixel-equivalence guarantee. The
separately documented reader corpus records observations for the named supported desktop/browser
matrix.

## Publication, history, and recovery

Destination commit and restart recovery reuse the PWS-0112 no-replace and prepared/committed retry
lifecycle. The flattened report's base structural report carries the flattened semantic
fingerprint into export-history-v1. Flattened-only checks remain transient; existing history and
manifest schemas are not reinterpreted. A history failure after verified destination reopen yields
the normal committed-history-pending outcome and never repeats the export.

## Accessibility, privacy, and portfolio effects

Progress is numeric and cancelable; errors are plain-language and actionable without source text,
OCR text, form values, names, paths, filenames, metadata, pixels, or native exception details.
Vector text and marks remain sharp when zoomed. This export path does not make a PDF/UA or complete
reading-order claim; the accessible editor and gate evidence remain separately tested.

The feature is independently useful in standalone PaperWorkShell and owns all of its data locally.
It introduces no sibling repository, shared SDK, service, database, workspace, adapter, release
cadence, or ThirdLife data access. `docs/release/RELEASE_INTERFACE.md` remains human-readable and
its unproved release fields remain `TBD`; no portfolio future note or synchronized release
dependency is created.
