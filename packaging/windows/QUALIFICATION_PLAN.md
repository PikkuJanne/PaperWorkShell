## Candidate and environment bindings

Before execution, bind each receipt to the exact installer and installed-file
inventory, source snapshot, dependency lock, SBOM/notices, product/package/upgrade
identities, version/channel and observed signing state. Record SHA-256 values
automatically and compare to the independently retained build receipt. A changed candidate requires new affected evidence.

Use a disposable clean Windows environment for each claimed supported x64
edition/build. Record OS facts, privilege state and installed
prerequisites automatically, with provenance. The guest must not require Python,
uv, Git, a compiler, an SDK or another development environment to install or run
PaperWorkShell. Keep build tools and signature-inspection tooling outside the
clean guest where practical; their presence must never conceal a missing runtime.

Use an actual standard-user account for normal launch and document work. Record
whether installation, repair and removal request elevation. Test any elevated
operation separately; an administrator's unelevated process alone does not prove
the standard-user claim. Do not publish account names or private absolute paths.

Only generated, cleared synthetic inputs are allowed. Keep originals, prior
exports and unrelated files as byte-hashed sentinels outside managed case storage.
Run native worker checks serially, following the
[quality-gate recovery rules](../../docs/development/quality-gates.md).

## Data choices and removal boundary

The [source review helper](../../src/paperworkshell/ui/uninstall_review.py) keeps
cases by default. It accepts no paths or switches. A separate, initially unchecked
choice requests review, followed by another unchecked confirmation and a distinct
deletion action. Its application service consumes consent once, works sequentially
and checks cancellation between cases. Inspection does not migrate or recover
manifests. Changed, unsupported or unsafe cases remain with truthful accounting.

The helper acquires `Local\io.github.pikkujanne.paperworkshell.App` before storage
inspection and holds it through the final acknowledgement. The packaged launcher
must hold the same mutex for normal app execution and refuse launches while review
is active. A separate-process source security check proves exclusion before the
helper's storage factory. Direct development launch outside the native launcher
does not hold this packaged lifecycle mutex; that path does not establish an
installed-app exclusion claim. Reviewed case directory identity and manifest hash
are checked again before deletion.

The packaged entry point is `python -I -B -m paperworkshell.ui.uninstall_review`.
Exit `0` permits application removal after an explicit user action; `1` cancels
it; `2` reports an initialization/argument failure. A deletion result must be
acknowledged before permission is returned. Silent removal skips this helper and
preserves data. The helper itself never removes installation files; the installer
must implement and qualify that integration.

Reuse [the lifecycle deletion adapter](../../src/paperworkshell/storage/case_lifecycle.py)
and [authenticated workspace removal](../../src/paperworkshell/storage/workspace.py).
They provide bounded inventory, manifest validation, pinned identities and refusal
of active or unsafe case state. Process cases sequentially and support cancellation
between cases. Do not add a recursive-delete fallback, accept a caller-supplied
arbitrary root or delete the entire application-data directory.

Unsupported, corrupt, partial or unsafe cases and unknown entries remain in place
with a truthful retained/failed count and actionable recovery guidance. Do not
automatically resume destructive work after restart. Never follow external source
or export paths in manifests. Verify external sentinels after both preservation
and explicit managed-case deletion.

The [existing export-preservation tests](../../tests/integration/test_post_export_deletion_windows.py)
and [case lifecycle security tests](../../tests/security/test_case_lifecycle_security.py)
provide reusable supporting cases; they do not replace installer evidence.

## Residue inventory

Record actual presence, ownership and disposition by category after each removal:

- Installer-owned binaries, bundled resources, optional engines/language data,
  notices, shortcuts and registration: remove according to the exact inventory.
- Cases under `<current-user-profile>\AppData\Local\PaperWorkShell\Cases`:
  preserve by default; confirmed authenticated deletion includes case originals,
  records, overlays/assets, derived files, previews, caches and case temporary data.
- Unknown entries, unavailable cases and empty retained roots: report explicitly;
  do not describe partial deletion as complete.
- Worker AppContainer profiles, private temporary storage and the
  `<LocalAppData>\PaperWorkShell.WorkerAclRecovery.v1` journal: use existing worker
  shutdown/recovery authority. Never discard an ACL recovery journal blindly.
- Configuration, persistent logs and migration backups: establish actual packaged
  behavior before documenting a target; do not invent stores or cleanup paths.
- External source documents, selected export destinations and user-selected support
  bundles: preserve. Application removal does not authorize their deletion.

Reflect observed facts in [the release interface](../../docs/release/RELEASE_INTERFACE.md)
and [evidence index](../../docs/release/RELEASE_EVIDENCE.md). Leave unknowns visibly
unproved; this plan is not a completed release checklist.

## Historical signed-variant plan

PWS-D044 superseded the mandatory signing provisions on 2026-11-26. The procedure
below is retained for context and applies only to a later separately approved signed
variant. Candidate qualification uses the unsigned identity and inventory checks above.

Use only the approved maintainer-controlled signing mechanism. Never request,
commit or log private keys, certificate passwords or signing-service credentials.
After application bytes are final, sign the selected application artifacts; build
the installer from those exact signed inputs, then sign the final installer.
Verify after every byte-changing packaging/signing step and hash the final outputs.

Check the approved signer identity, signature validity, timestamp/trust behavior
under the approved policy and the exact packaged inventory. A valid signature by
an unapproved publisher is insufficient. Include tampered and wrong-signer negative
controls. No signed-artifact claim is permitted until these checks actually pass.
